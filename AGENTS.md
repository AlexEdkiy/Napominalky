# Napominalky

Продукт: local-first заметки, задачи/списки покупок, напоминания и календарь.
Mobile хранит данные в SQLite/Drizzle, backend Laravel обслуживает API/sync,
web Vue — личный кабинет и админку. Сохранность данных важнее новых UI-фич.

## Начало работы

- Прочитай `docs/DEVELOPMENT.md` (текущий фокус, проверки, передача работы),
  актуальную задачу в `docs/TASKS.md` и стандарты только затронутого слоя.
- `CLAUDE.md` и `.claude/agents/` описывают команду Claude; они не запускают её
  в Codex. Используй доступные инструменты сессии, не имитируй вызовы TaskCreate.
- В одиночной сессии координатор может реализовывать и проверять задачи сам.
  Самопроверка должна быть названа самопроверкой, а не независимым ревью.
- При расхождении старого регламента с этим файлом и `docs/DEVELOPMENT.md`
  используй эти актуальные правила работы. Историю задач не переписывай.

## Работа с репозиторием

- С OPS-18 production находится на `devops@195.206.252.160`: `reminders_serve`
  и `reminders_web` читают неизменяемые `/srv/napominalky/releases/`;
  `.env`, пользовательские файлы и логи — `/srv/napominalky/production/`.
  Локальный `Napominalky-runtime` — прежняя площадка/артефакты для упаковки,
  не активный production. Активный релиз определяй по labels на новом VPS
  и `https://lk.napominalky.ru/release.json`. Сверяй состояние DNS по OPS-18.
- Разрабатывай в отдельном worktree. Выпуск выполняется только через
  `deploy/releases/` по проверенному SHA; merge/сборка в dev не выкладывают код.
  Сначала подготовь diff и план выпуска; учитывай разрешение пользователя.
  Команды, результаты и откат: `deploy/releases/README.md`.
- Старые контейнеры `*-legacy-*` остановлены. После переноса не запускай их:
  там прежнее хранилище. Откат кода использует baseline-артефакт и актуальные данные.
  Старые writers/scheduler выключены, старая БД read-only: не возвращай ей запись.
  Рабочие DB/Redis на новом VPS выделены отдельно; не выполняй `docker compose down`
  и не используй production для тестов. Для проверок нужна отдельная БД.
- Сохраняй текущие API-контракты и семантику SQLite/outbox/LWW/tombstone.
  Новые контракты и схемы сначала опиши как отдельное архитектурное решение.
- ID резервируй в TASKS.md перед работой. У реестра один автор на цикл;
  счётчики означают последний выделенный ID, статусы — фактическую готовность.
- Проверки выполняй из своего worktree. `docker exec reminders_app` проверяет
  основную копию, а не твою ветку: нельзя использовать его как доказательство
  проверки изменённого backend. Для backend ветки нужен отдельный контейнер.
- По указанию пользователя каждый этап sync проверяй также со стороны mobile:
  реальные функции/хуки → SQLite/outbox, поля для экранов, офлайн/повтор/новая правка
  во время запроса и выход/смена аккаунта. Ожидания и результаты — в отчёте задачи.
  Моки HTTP/нативных модулей и Node SQLite отдельно от устройства/E2E; копия
  бизнес-логики внутри теста не заменяет вызов проверяемого production-кода.
- Коммиты: `[TASK-ID] описание`, без force push, rebase и изменения общей Git identity.
  В отчёте указывай ветку, SHA/рабочий diff, проверки, ограничения и следующий шаг.
