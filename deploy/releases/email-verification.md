# Подключение почты и выпуск MOB-74 / MBE-24

На 2026-10-14 production использует `MAIL_MAILER=log`; реальной доставки нет.
Существующие пользователи не требуют повторного подтверждения. Выпуск нового сервера
с обязательным подтверждением должен идти после настройки доставки и вместе с web.
Новый APK публикуется после сервера. До этого остаётся действующий APK 1.0.5 (48).

Публичный DNS на 2026-10-14: NS сервиса RU-CENTER (`*.nic.ru`), MX и TXT для корня
в ответе отсутствуют. Записи потребуется добавить в панели, управляющей этой DNS-зоной.

## Что нужно от владельца

1. Зарегистрировать аккаунт почтового транспорта. Предложен Unisender Go; покупка тарифа
   и регистрация за владельца не выполнялись. Можно использовать другой SMTP-сервис.
2. В его кабинете добавить домен `jemsoft.ru`. Доступ к панели DNS обязателен.
3. Добавить выданные сервисом записи подтверждения, SPF и DKIM. DKIM и запись владения
   индивидуальны — не копировать чужие значения. Не создавать второй SPF: объединить
   разрешённых отправителей в существующем, если он уже есть. Не менять A/AAAA сайта.
4. Дождаться подтверждения домена в кабинете, выбрать отправителя `noreply@jemsoft.ru`.
   Ответы пользователей при необходимости направлять на отдельный действующий адрес.
5. Сохранить SMTP-реквизиты в `/home/vselug/workspace/Napominalky-runtime/production/.env`
   через защищённый редактор. Не присылать ключ в чат, не писать его в shell-команду/Git.

Параметры для Unisender Go: host соответствует кабинету go1/go2, username — user_id
или project_id, password — API-ключ. Поддерживается SMTP с TLS.
[SMTP-инструкция](https://godocs.unisender.ru/smtp-api),
[подтверждение домена](https://godocs.unisender.ru/web-api-ref).

Шаблон для текущего Laravel (значения в угловых скобках заменить в редакторе):

```dotenv
MAIL_MAILER=smtp
MAIL_SCHEME=smtp
MAIL_HOST=<smtp.go1.unisender.ru или smtp.go2.unisender.ru из кабинета>
MAIL_PORT=587
MAIL_TIMEOUT=5
MAIL_USERNAME=<user_id или project_id>
MAIL_PASSWORD="<API-ключ>"
MAIL_FROM_ADDRESS=noreply@jemsoft.ru
MAIL_FROM_NAME="Напоминалки"
FRONTEND_URL=https://jemsoft.ru/napominalki
```

На 587 используется STARTTLS; проверку сертификата не отключать. Если уже задан
`MAIL_URL`, проверить его приоритет и убрать конфликт с отдельными SMTP-настройками.
Отключить отслеживание ссылок/прочтений для служебных писем в кабинете сервиса.
Данные SMTP не передаются в Expo и не включаются в APK.

## Проверка перед выпуском

- Проверить DNS, SMTP/TLS-подключение и корректность отправителя без вывода ключей.
- С согласованным тестовым адресом пройти настоящую регистрацию: доставка, ссылка
  на `https://jemsoft.ru/napominalki/verify-email`, подтверждение и вход. Отправка на
  адрес реального человека учитывается отдельно; локальные тесты используют fake/log.
- Провести проверку артефакта и миграции только в изолированной БД. Миграция добавляет
  `users.email_verification_required=false`, не меняет пароли и существующие отметки.
- Выпустить backend и web одним проверенным SHA через штатный managed release.
  Ссылку обслуживает новый web; его нельзя оставить на прежнем релизе.
- После проверки сервера собрать Expo preview APK и проверить тот же сценарий на телефоне.
  Старые APK смогут входить в существующие аккаунты; для новой регистрации нужно обновление.

## Откат

Предпочтителен исправляющий релиз с сохранением проверки почты. Старый backend
WEB-69 не знает о `email_verification_required`: простой откат позволит новым
неподтверждённым аккаунтам входить. Не откатывать миграцию и не удалять аккаунты.

Если необходим именно старый код: сначала временно закрыть регистрацию на прокси,
сохранить список UUID активных неподтверждённых новых аккаунтов и временно отключить
только их (`is_active=false`), затем переключать артефакт. После восстановления нового
кода вернуть активность только сохранённым UUID. Эти действия затрагивают доступ
пользователей и требуют отдельного плана выпуска; автоматически они не выполнялись.
