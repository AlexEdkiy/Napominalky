# WEB-70 — пустая карточка после удаления задачи

Дата: 2026-10-29. Самопроверка автора: Codex.
Исследованный production: `r3bb319c-mob75`, SHA `3bb319c`.
Координация: `manage-2026-09-30`; изменения исходного кода в этом инциденте отсутствуют.

## Подтверждённая причина

Проверка PostgreSQL в READ ONLY транзакциях обнаружила все пункты в таблице,
но с заполненным deleted_at. Активный родитель остался с закреплённым ручным статусом.
Реальный production Items\IndexController под владельцем задачи возвращает data=[]
и meta.total=0. Контроллер вызван внутри отдельного PHP-процесса и READ ONLY транзакции;
это не авторизованный HTTP-сеанс браузера и не UI/E2E проверка.

Журнал sync_conflicts содержит клиентскую версию родителя с deleted_at и более новой
серверной версией без deleted_at. Чтение выпущенного кода объясняет последовательность:

1. Mobile ShoppingListsRepository.deleteList создаёт tombstones активных пунктов,
   затем tombstone родителя.
2. SyncPushService последовательно применяет изменения. Удаление пункта вызывает
   RecalculateListStatusAction; даже закреплённый статус не блокирует пересчёт дат.
3. При изменении производной даты save() обновляет updated_at родителя серверным now.
4. Позднее клиентское удаление родителя сравнивается с этим новым updated_at и получает
   конфликт server-wins. Дети уже удалены, родитель остаётся видимым.

Размер списка не был причиной этого случая. Пользователь подтвердил, что намеренно
удалял задачу целиком; восстанавливать её пункты не требовалось.

## Завершение удаления

Перед изменением сохранена локальная закрытая JSON-копия только затронутой задачи,
её пунктов и комментариев. Права 0600, checksum записан отдельно. В публичный Git
не включены копия, идентификаторы, заголовок, содержимое пунктов и комментариев.

Одноразовая операция использовала существующий DeleteListAction в DB-транзакции:
проверка владельца, FOR UPDATE, ожидаемой версии и полного хеша сохранённых записей,
отсутствия новых активных пунктов; затем мягкое удаление оставшегося родителя.
Перед commit проверены отсутствие в активной выборке, рост server_revision, наличие
родительского tombstone в настоящем SyncPullService и побайтная неизменность данных
детей/комментариев. Отдельное чтение после commit подтвердило результат.

Выполнено 2026-10-29, 11:19:58 МСК. Данные физически не удалялись. Пункты и комментарии
не восстанавливались и не менялись; исходный отдельный старый tombstone также сохранён.
Контейнеры, код, конфигурация и схема production не изменялись.

Закрытые материалы: `Napominalky-artifacts/web70/` — `diagnosis-private.json`,
`pre-repair-private.json`, `backup-sha256.txt`, `finish-confirmed-delete.php`,
`repair-receipt-private.json`. Одноразовая операция отклоняет повторное выполнение
и любые изменения после снимка; для нового восстановления требуется новый план
и новая синхронизационная ревизия, а не загрузка старой записи поверх актуальной.

## Ограничения и дальнейшая работа

WEB-70 закрывает диагностику и оставшуюся карточку конкретного удаления.
Общая ошибка синхронизации остаётся: создана DEV-26 с критическим приоритетом.
Просто переставить родительское удаление в начало одного push недостаточно для
очередей, разделённых лимитом 500. Также нельзя безусловно принимать старое удаление
поверх настоящей более новой правки другого устройства. Решение требует отдельной
проверки версии пользователя и производного пересчёта, совместимой с ARCH-4.

Новый backend/mobile/web suite и сборки не запускались: исходники не менялись.
Работа на физическом телефоне и обновление уже открытого браузерного экрана здесь
не проверялись. Получение tombstone подтверждено реальным серверным сервисом; клиентам
нужно обновить данные/выполнить синхронизацию.
