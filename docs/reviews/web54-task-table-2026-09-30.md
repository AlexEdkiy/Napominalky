Основание изменений: пользовательский запрос из четырёх пунктов и уточнение

## Поведение

- Только клик по наименованию открывает карточку задачи. Клик по пустой области,
  счётчику пунктов или полям карточку не открывает; клавиатура работает через кнопки.
- Статус выбирается из меню. Теги, дедлайн и напоминание редактируются в небольшом
  окне у поля. Есть сохранение, очистка, отмена, обработка ошибок с сохранением
  ввода и блокировка повторной отправки. Напоминание показывает дату и время.
- Общие даты сохраняются на сервере и не теряются после перезагрузки. Если общий
  дедлайн 15.10.2026, а у невыполненного пункта 12.10.2026, итог — 12.10.2026.
  Аналогично для напоминания, независимо от дедлайна. Завершённые и удалённые пункты
  исключены; просроченные невыполненные учитываются. После завершения раннего пункта
  возвращается общая настройка либо более ранняя дата другого активного пункта.
- Подсказка над счётчиком пунктов показывает их названия и отметки выполнения.
  Комментарии в ней не показываются. Для покупок сохранены прежние действия.

[Контракт и решение по схеме](../architecture/task-list-schedule.md): четыре nullable
колонки у shopping_lists, публичные итоговые deadline/reminder_at и внутренние
manual_deadline/manual_reminder_at. Отсутствие поля в PUT/sync не очищает настройку;
явный null очищает только общую настройку, а не даты пунктов.

Мутация пункта и пересчёт родителя выполняются в одной транзакции. Ошибка записи
родителя откатывает пункт. Родитель блокируется при пересчёте и изменении списка
через REST/sync; перенос пункта через sync пересчитывает обе задачи. Общая задача
DEV-24/B о порядке ревизий и блокировок всех writers этим не закрывается.

## План выпуска и откат

1. Опубликовать коммит ветки, проверить GitHub Actions именно для выпускаемого SHA:
   backend, mobile checks, web checks. Источник CI —
   [Actions ветки](https://github.com/AlexEdkiy/Napominalky/actions?query=branch%3Amanage-2026-09-30).
2. По этому SHA подготовить неизменяемый артефакт через `deploy/releases/prepare.py`
   и проверить manifest через `runtime.py verify`. В production попадёт также уже
   проверенная backend-часть DEV-24/A; изменения относительно активного `9cb10c6`
   необходимо учитывать целиком, а не только diff WEB-54. Схема получает только
   миграцию `2026_09_30_120000_add_schedule_to_shopping_lists_table.php`.
3. Перед выпуском сохранить резервную копию production БД вне Git. Кратко остановить
   запись и scheduler на время миграции/переключения: backfill меняет даты и ревизии,
   одновременно старый код ещё не умеет поддерживать новые итоговые колонки.
4. Из контейнера нового артефакта выполнить `php artisan migrate --force` с production
   окружением, затем переключить backend/web через `deploy/releases/switch.py`.
   Switch самостоятельно миграции не запускает. Проверить health/API/web/release SHA,
   восстановить запись/scheduler, проверить сохранение общей даты и приоритет пункта.
5. При проблеме откатить только код на активный предыдущий артефакт тем же switch.py,
   сохранив актуальные БД/storage и новые nullable колонки. `migrate:rollback`/`down`
   на production не выполнять. Если старый код после отката изменял пункты, перед
   повторным выпуском пересчитать итоговые даты всех tasks новым resolver, сохранив
   manual-поля; уже выполненный backfill повторно сам не запустится.

Runbook: [deploy/releases/README.md](../../deploy/releases/README.md).
Локальная реализация и тесты не означают production-выпуск. Рабочая БД и активный
артефакт в ходе WEB-54 не изменялись.
