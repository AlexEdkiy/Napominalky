# MOB-71 — перенос даты пункта и красный будильник

Дата: 2026-10-03. Ветка: `manage-2026-09-30`. Самопроверка Codex.

## Результат диагностики

Пользователь уточнил, что 13 октября выбиралось в поле **«Дедлайн»** в свойствах
пункта. Это отдельное поле от «Напоминание». Календарный чип mobile показывает
`deadline`; маленький колокольчик показывает только наличие `reminderAt`, без даты.
Поэтому снимок календарного чипа не подтверждает перенос напоминания.

Проверка конкретной задачи в production выполнена только на чтение, внутри
`SET TRANSACTION READ ONLY`: дедлайн пункта и общий дедлайн уже перенесены,
напоминание пункта и общее напоминание остаются на прежнем дне. Общие даты ручным
значением не закреплены. Конфликтов sync по пунктам этой задачи за день обращения
нет. Пользовательские даты, аккаунт, очередь и production-код не менялись.

Web соответствует WEB-58: красный будильник включается при дедлайне **или**
напоминании на сегодня у активной задачи/пункта. Ошибка синхронизации в этом
сценарии не подтверждена. Для переноса сигнала нужно изменить поле «Напоминание».
Рекомендуемое отдельное улучшение интерфейса: показывать рядом с колокольчиком дату
и время, чтобы не путать их с дедлайном. Автоматическая связь сроков не добавлена.

## Добавленная регрессия

`mobile/src/components/lists/__tests__/item-schedule-flow.test.tsx` вызывает
настоящий экран `app/lists/[uuid].tsx`, TanStack hooks, repositories, Expo Drizzle
на Node SQLite и `pushChanges`/`applyChanges`. Моки только native bridges и HTTP.
Проверены четыре сценария:

1. Android «Напоминание → Своё время → дата → время» меняет `reminderAt`, обновляет
   строку редактора и отправляет `reminder_at` в sync; дедлайн остаётся прежним.
2. «Дедлайн → Выбрать дату» меняет только `deadline`; старое напоминание сохраняется.
3. Отмена выбора времени не сохраняет неподтверждённый шаг даты.
4. Старый pull и отклонённый push не удаляют новую дату/очередь; повторный push
   отправляет ту же новую дату и очищает только подтверждённую запись.

## Уточнение после диагностики

Пользователь уточнил требуемую семантику: красный будильник должен зависеть только
от дедлайна. Предыдущее описание WEB-58 выше отражает прежнее поведение; новое
условие реализуется в [WEB-64](web64-deadline-alarm-2026-10-03.md).
