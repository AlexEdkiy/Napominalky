## Найдено и исправлено

`useAuth.tryFlushSync` считал любой push без исключения успешным сохранением всех
правок. HTTP success с неподтверждённой записью или правка, созданная во время push,
оставляли outbox непустым. Затем `performLogout` удалял данные без предупреждения.
Теперь после push проверяется фактическое наличие строк в SQLite outbox. Остаток
очереди или ошибка проверки ведут к существующему диалогу: «Отмена» сохраняет данные
и сессию, «Выйти» разрешает очистку. Это предварительное исправление из согласованного
ARCH-4; полная реализация этапа D ещё впереди.

Прежние 16 тестов useAuth вызывали копии алгоритмов `runLogoutFlow/runOnAuthSuccess`,
а не product-код. Они заменены 10 интеграционными сценариями: настоящий `useAuth`
монтируется с React Query через `renderHook`, используется реальный push/reset/meta,
доменные репозитории и SQLite. Подменяются только API, auth storage, навигация,
соединение DbProvider и нативные внешние действия. На прежнем product-коде **3 failed /
7 passed**, после исправления **10 passed**. Проверены обе кнопки предупреждения,
пустая/полностью подтверждённая очередь, неподтверждённая/новая правка и ошибка push.
При входе проверяются guest/same-account/другой аккаунт без неотправленных правок:
метаданные и нулевой cursor готовы до публикации нового token.

## Путь данных мобильного клиента

Шесть дополнительных тестов `mobileSqliteFlow.test.ts` вызывают реальные функции:
`pullChanges → applyChanges → mappers → SQLite → мобильные репозитории`, а затем
репозиторий → outbox → `pushChanges`. HTTP-граница `syncApi` возвращает заданные
контрактные ответы; это не сетевой E2E с работающим backend.

Проверены:

- Две страницы pull, ссылки list/item/comment, все пять типов сущностей, booleans,
  статусы и ранее потерянные семь полей доступны через репозитории, читаемые экранами.
- Явная очистка color/метаданных пункта и изменение quantity удаляют прежние значения.
- Повторный pull сохраняет локальные notification_id и calendar_event_id.
- Правка заголовка не теряет остальные поля в полном snapshot следующего push.
- SQL-сбой удаления подтверждённых строк сохраняет точную очередь и draft;
  последующий push повторяет прежний payload и очищает очередь после успеха.
- Входящие tombstones скрываются из мобильных выборок и не создают исходящую очередь.

SQLite и Drizzle настоящие (все миграции, установленный Expo driver); statement bridge
использует Node SQLite, как в DEV-24/A. UI-render экранов и физические уведомления этими
сценариями не проверялись. Доступного через PATH adb/emulator нет; native-прогон не заявляется.

## Оставшиеся мобильные риски

Полнота payload и logout guard не закрывают весь sync. По ранее подтверждённому ARCH-4:
ложный v1 applied при orphan всё ещё может очистить очередь (этап C); pull может заместить
pending более новой серверной версией и продвигает cursor после ошибки записи; защита
in-flight/account-switch, durable inbox и quarantine остаются этапом D. Монотонные
локальные timestamps также впереди. Мобильный рендер всех восьми цветов остаётся MOB-66.
Эти гарантии не приписываются текущим проходящим тестам.

Очередной основной этап — DEV-24/B. Для каждого его изменения добавляется проверка
мобильного потребителя соответствующего контракта. Перед выпуском нужны устройство,
crash/restart, двухклиентный E2E и независимое ревью из этапа E.

API тестового рендера сверено с установленной библиотекой и
[официальной документацией renderHook](https://oss.callstack.com/react-native-testing-library/docs/api/misc/render-hook).
