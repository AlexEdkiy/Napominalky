# SEC-2 / OPS-21: границы инцидента Redis и отключение Insure Platform

Дата: 2026-11-19. Исполнитель: Codex, самопроверка. Запрос пользователя: проверить
соседние сервисы, данные/секреты и следы дальнейшего проникновения; затем явно
разрешено вывести Insure Platform из эксплуатации. Диагностический этап SEC-2
и отключение OPS-21 завершены. Инцидент не объявлен закрытым, чистота всего хоста
не доказана. Полный offline forensic-аудит и ротация секретов не выполнялись.

## Что такое Insure Platform

Отдельный проект «Страхование жилья по подписке», README:
`/home/vselug/.openclaw/workspace/insure-platform/README.md`.
Node.js/Express/Prisma API, Next.js frontend, PostgreSQL, Redis и mock платёжный
шлюз. Есть OTP-вход, клиенты, подписки, полисы, платежи и административный интерфейс.
Шлюз имитирует платежи; это не свидетельство реального процессинга карт.

Docker labels указывают Compose-проект `insure-platform` и тот же рабочий каталог.
Первоначальные Redis, PostgreSQL и gateway созданы 22 апреля 2026, API/web — 27 апреля.
Автор развёртывания по этим метаданным не устанавливается. Это не часть Напоминалок,
но они использовали общий proxy и Docker-сеть `insure-platform_default`.

## Подтверждённые артефакты атаки

Архив получен до пересоздания Redis; файлы анализировались как данные, не исполнялись.
Пользователь прямо подтвердил, что майнинг не принадлежит администраторам.

| `/tmp/.xm.log` | Журнал XMRig, даты 31 октября — 5 ноября, 69 сообщений accepted |
| `/tmp/xmrig-managed-fb94925a324f91f8eff6f46a/xmrig` | ELF, 8 350 992 байта, строки XMRig |

SHA-256 `.sys`: `fd11982f252c060a1372e81d5be57589647052b56281a5c54975ca22164f7726`.
SHA-256 `xmrig` и `[kworker0:1H]`: `b20f39fc00d242e706b6c30367ad811c676e0575050a4ec2f30104b696944b49`.
Даты журналов не равны доказанной дате первоначального проникновения; файловые
mtime могут быть подделаны. Связь конкретного майнера с четырьмя ключами не доказана.
Адреса из вредоносных строк не посещались, код не скачивался.

Четыре ключа перенеслись в новый контейнер вместе с data volume в OPS-20. Сам Redis
не исполняет строки из ключей как cron. Их наличие всё же означает, что перенос
тома не был очисткой данных. Теперь этот контейнер и том выведены из эксплуатации.
На момент проверки MODULE LIST и FUNCTION LIST были пусты в обоих работающих Redis.

Полный Redis-журнал: 22 апреля — 19 ноября, 7 356 124 строки. В нём 335 событий
включения репликации, первые внешние slaveof — 24 апреля. 16 ноября клиент
47.95.226.208 менял master и инициировал загрузку данных с внешнего узла.
Диагностические записи содержат 19 058 crash reports и упоминания EVAL с 21 октября.
Это не полный аудит команд и не доказательство конкретного CVE или успешности
каждой попытки. Связь с Nginx2Root не установлена.

## Доступ к соседям и данные

Проверено из network namespace Redis, только TCP connect, без эксплуатации.

| Цель | До отключения Insure | Вывод |
|---|---|---|
| Insure API, PostgreSQL, web, mock gateway | Доступны | Соседние поверхности атаки в общей сети |
| API Напоминалок `172.18.0.7:8000` | Доступен | Прямой доступ к HTTP API, не доказательство обхода авторизации |
| PostgreSQL/Redis Напоминалок `172.19.0.2/3` | Timeout | Прямое подключение в момент проверки блокировалось |
| Staging API `172.20.0.3:8000` | Timeout | Отдельная сеть |
| SSH хоста через gateway сети | Доступен | Требуется ключ; посторонних успешных SSH-входов в проверенном периоде не выявлено |
| Docker API 2375/2376, host DB/API, VNC/X11 | Timeout | Доступ из Redis этим путём не подтверждён |

Redis работал с UID 999, без эффективных capabilities, с seccomp; privileged=false,
без host PID и без Docker socket. Единственный mount — `/data`; секреты API,
SSH-ключи и файлы Напоминалок прямо в Redis не монтировались.
Это ограничивает очевидные пути доступа, но не исключает kernel/container escape.

Работающий код Insure API сверён с файлами образа:

- OTP хранится в Redis открытым текстом; verifyOtp доверяет значению из Redis.
  Запись в Redis позволяла подменить OTP и потенциально получить пользовательскую
  сессию. Реальные захваты аккаунтов этой проверкой не доказаны.
- OTP также выводится в журнал API. Значения и телефоны в отчёт не включены.
- ADMIN_TOKEN совпадал со стандартным значением исходников. GET admin/stats без
  токена → 401, с настроенным стандартным токеном → 200 как через loopback API,
  так и через HTTPS jemsoft.ru. Тело статистики не сохранялось. После OPS-21 маршрут → 410.
- JWT, webhook, gateway и Telegram-секреты были заданы. Проверенные JWT/webhook/gateway
  не совпали с исходными fallback-значениями; это не доказывает их стойкость или отсутствие утечки.
- API подключался к PostgreSQL под bootstrap-superuser. Пароль короче 16 символов;
  сетевой вход требует SCRAM. Доказательства успешного подбора пароля не найдены.

В историческом Nginx access log найдено 44 успешных обращения к конкретным admin API
27–28 апреля с 91.225.27.7 и 81.92.203.66. Принадлежность этих адресов не проверена;
они не объявляются атакующими. Часть запросов PATCH меняла статус подписок.
Прямые обращения к ранее открытому порту 3000 обходили Nginx и этим журналом не покрыты.

## Проверки БД, Напоминалок и хоста

- В старом Insure PostgreSQL-журнале за 22 апреля — 19 ноября: 353 986 сообщений
  password authentication failed. Признаков COPY PROGRAM и известных miner-строк
  выбранным поиском нет. Успешные входы и SQL не логировались: log_connections=off,
  log_statement=none. Нельзя заключить, что чтения/изменения данных не было.
- В обеих PostgreSQL только ожидаемая login-role проекта, но обе superuser.
  В шести доступных базах, не являющихся шаблонами, нет функций вне штатных расширений;
  в основных БД нет event triggers и preload libraries. Insure: plpgsql;
  Напоминалки: plpgsql + pg_trgm. Это не полный аудит целостности строк БД.
- 335 tracked backend-файлов production совпали с Git `9e7ac28`;
  `.github/workflows/deploy.yml` отсутствует в runtime-артефакте. Других различий
  среди проверенных файлов нет. Vendor/frontend полной проверкой исходников не покрыты.
- `/.env` и `/.git/config` на API Напоминалок → 404, маркеры секретов не выдаются.
  `/up` → 200. Штатный smoke проверяет правильный `/api/v1/auth/me` и пустой login.
- В 54 файлах production storage и 52 dev storage не найдены ELF и выбранные
  индикаторы webshell/майнера. Исключены logs, symlinks и файлы >2 МБ.
- Ранее проверены writable layers 89 контейнеров: известные miner-paths только
  в старом insure_redis. Docker diff не охватывает содержимое томов и образов.
- В 63 файлах автозапуска/профилей хоста не найдены домен/строки четырёх вредоносных
  ключей. Нет `/etc/ld.so.preload`, единственная UID 0 учётная запись — root.
- `dpkg -V openssh-server openssh-client sudo coreutils bash libc6 systemd cron`:
  exit 0, без отличий. Использована локальная база пакетов, не независимый эталон.
- SSH root/password login выключены. Успешные SSH-входы 18 октября — 19 ноября
  только vselug/publickey с трёх адресов, подтверждённых владельцем. История до
  18 октября этой проверкой не покрыта; происхождение каждого authorized key не доказано.

## Остаточный риск Redis Напоминалок

Оба Redis до отключения Insure были версии 7.4.8. У оставшегося reminders_redis
default ACL: nopass, +@all; protected-mode=no, при этом порт не опубликован наружу.
Доступ ограничен сетью проекта, но скомпрометированный backend может обращаться к нему.
В 7.4.9–7.4.12 исправлены дополнительные ошибки безопасности, включая RCE в RESTORE
и Lua. Следующий технический приоритет — обновление reminders_redis в ветке 7.4
до проверенного актуального patch release, отдельная ACL для приложения и запрет
ненужных административных команд. Не загружать подозрительные RDB в старый Redis.

Источники, проверены 2026-11-19:
- [Официальные release notes 7.4.12](https://raw.githubusercontent.com/redis/redis/7.4.12/00-RELEASENOTES).
- [Redis advisory RESTORE](https://github.com/redis/redis/security/advisories/GHSA-c8h9-259x-jff4).
Версия 7.4.8 уязвима по release notes; наличие конкретного CVE в данном проникновении не доказано.

## OPS-21: что отключено и как проверено

1. Убраны upstream api/web/gateway из общего Nginx. Их 12 location-блоков в
   IP HTTP и Jemsoft HTTPS заменены на return 410. Сначала отдельный nginx -t,
   затем запись с сохранением bind-mounted inode, nginx -t и reload.
2. У всех пяти Compose-сервисов restart=no и profile retired. Compose config
   --services без включения профиля вернул пустой список. Отдельных cron/systemd
   ссылок на Insure Platform не найдено.
3. Остановлены пять текущих контейнеров; у них и пяти before-ops20 restart=no,
   все сети отсоединены. Старый заражённый Redis не запускался.
4. Сохранён финальный cold snapshot тома PostgreSQL после остановки (10 040 708
   байт) и dump.rdb Redis (577 байт); исходные volumes и контейнерные журналы сохранены.
   Попытка финального pg_dump до завершения graceful stop приложений была отменена
   проверкой состояния; действительный финальный бэкап — cold volume archive.
5. 21 проверка прежних маршрутов → 410; loopback 3000/3001/3002/5432/6379 закрыты.
   nginx -t успешен. Все 41 прежние проверки HTTP/TLS/asset остальных сайтов прошли.
   Штатный production smoke Напоминалок прошёл. ID, состояние и StartedAt остальных
   контейнеров не изменились; proxy только reload.
6. README Insure помечен архивным. Общая сеть, nginx-proxy, Jemsoft landing,
   certbot, Напоминалки и Mafin сохранены. Каталог Insure пока нужен общему Nginx:
   **не удалять его до отдельного переноса nginx.conf**.

Возвращать Insure из этих снимков в публичную работу нельзя. Для возможного
восстановления нужен новый защищённый runtime, ротация административного/JWT/DB
доступа, отзыв сессий и выборочный перенос проверенных данных. Старые secrets
в сохранённых материалах считать чувствительными; материалы не публиковать.

## Доказательства и следующие шаги

Все каталоги приватные, вне Git:
- `Napominalky-runtime/ports-security-20261119/`: исходный export Redis (76 239 872
  байта), SHA-256, полный журнал (528 784 990 байт), timeline, исходные настройки.
- `Napominalky-runtime/redis-incident-sec2-20261119/`: карта сети/секретов без значений,
  read-only проверки API/БД, вредоносные ключи в приватном JSON, результаты сверки.
- `Napominalky-runtime/insure-retirement-20261119/`: before/candidate конфигурации,
  снимки состояния, cold PostgreSQL archive, Redis dump, verification и SHA-256.

План дальнейших мер:
1. Обновить и ограничить ACL оставшегося Redis Напоминалок; проверить очереди,
   cache, расписание и синхронизацию, сохранить данные и резервный план.
2. Разделить proxy/app/data сети; приложениям выделить DB-роли без superuser.
3. Определить судьбу внешних секретов архивного Insure (например, Telegram bot token):
   остановка контейнеров не отзывает их у провайдера. Утечка этих секретов не доказана.
4. Для восстановления доверия к хосту — план нового чистого сервера с переносом
   проверенных артефактов/данных и последовательной ротацией реально используемых
   секретов. APP_KEY Напоминалок не менять вслепую: сначала проверить шифрованные данные.

Чтение личных memory/profile файлов, упомянутых в локальном AGENTS.md, отклонено
автоматической проверкой как нерелевантное и чувствительное; обхода не было.
Техническая диагностика и отключение проекта завершены без этих файлов.
