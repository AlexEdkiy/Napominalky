# 1. Общие положения

## Философия

> The Zen of Python — Tim Peters

- Красивое лучше, чем уродливое.
- Явное лучше, чем неявное.
- Простое лучше, чем сложное.
- Сложное лучше, чем запутанное.
- Плоское лучше, чем вложенное.
- Разреженное лучше, чем плотное.
- Читаемость имеет значение.
- Особые случаи не настолько особые, чтобы нарушать правила.
- При этом практичность важнее безупречности.
- Ошибки никогда не должны замалчиваться.
- Если они не замалчиваются явно.
- Встретив двусмысленность, отбрось искушение угадать.
- Должен существовать один и, желательно, только один очевидный способ сделать это.
- Хотя он поначалу может быть и не очевиден.
- Сейчас лучше, чем никогда.
- Хотя никогда зачастую лучше, чем прямо сейчас.
- Если реализацию сложно объяснить — идея плоха.
- Если реализацию легко объяснить — идея, возможно, хороша.
- Пространства имён — отличная штука! Будем делать их больше!

## Базовые правила

- Используйте понятные и читаемые названия.
- Используйте английские слова, обозначающие суть.
- Разделяйте код на логические блоки.
- Сокращайте вложенность.
- Не допускайте дублирования.
- Контролируйте длину:
  - строка — не более 120 символов
  - функция — не более 20 строк
  - метод — не более 50 строк
  - класс — не более 300 строк
  - файл — не более 1000 строк
- Документируйте код.
- Комментируйте код при необходимости.
- Используйте рефакторинг.
- Используйте Git.

## Принципы

### DRY (Don't Repeat Yourself)

Дублирование кода — пустая трата времени и ресурсов. Вам придется поддерживать одну и ту же логику и тестировать код сразу в двух местах, причем если вы измените код в одном месте, его нужно будет изменить и в другом. В большинстве случаев дублирование кода происходит из-за незнания системы. Прежде чем что-либо писать, проявите прагматизм: осмотритесь. Возможно, эта функция где-то реализована. Возможно, эта бизнес-логика существует в другом месте. Повторное использование кода — всегда разумное решение.

### KISS (Keep It Simple, Stupid)

Будь проще. Иногда самое разумное решение оказывается и самым простым. Одна из самых распространенных ошибок нашего времени — использование новых инструментов исключительно из-за того, что они новые, а не потому, что они подходят для решения задач.

### YAGNI (You Aren't Gonna Need It)

Вам это не понадобится. Если пишете код, то будьте уверены, что он вам понадобится. Не пишите код, если думаете, что он пригодится позже. Этот принцип применим и при рефакторинге. Если вы занимаетесь рефакторингом метода, класса или файла, не бойтесь удалять лишние методы. Даже если раньше они были полезны — вы сможете восстановить их из git-репозитория.

### Big Design Up Front

Глобальное проектирование прежде всего. Прежде чем переходить к реализации, убедитесь, что всё хорошо продумано. Составив план, вы избавите себя от необходимости раз за разом начинать с нуля.

### Avoid Premature Optimization

Избегайте преждевременной оптимизации. Предвидеть, что произойдет что-то плохое — это хорошо. Но прежде чем вы погрузитесь в детали реализации, убедитесь, что эти оптимизации действительно полезны.

### Occam's Razor

Не следует привлекать новые сущности без крайней на то необходимости. Не создавайте ненужных сущностей без необходимости. Будьте прагматичны — подумайте, нужны ли они, поскольку они могут в конечном итоге усложнить вашу кодовую базу.

### SOLID

- **S** — Принцип единственной ответственности — каждый объект, класс и метод должны отвечать только за что-то одно.
- **O** — Принцип открытости-закрытости — программные объекты должны быть открыты для расширения, но закрыты для модификации.
- **L** — Принцип подстановки Лисков — объекты старших классов должны быть заменимы объектами подклассов, и приложение при такой замене должно работать так, как и ожидается.
- **I** — Принцип разделения интерфейсов — много интерфейсов, специально предназначенных для клиентов, лучше, чем один интерфейс общего назначения.
- **D** — Принцип инверсии зависимостей — мы должны полагаться на абстракции, а не на конкретные реализации.

## Версии стека

### Политика версий

Проект использует **максимально доступные стабильные версии** пакетов и фреймворков. При разрешении конфликтов отталкиваемся от базовых версий стека.

### Базовый стек

| Компонент | Версия | Примечание |
|-----------|--------|------------|
| **PHP** | 8.5+ | Базовая версия, определяет совместимость всех PHP-пакетов |
| **Laravel** | 12+ | Основной фреймворк |
| **PostgreSQL** | 17+ | СУБД, использовать native типы и возможности |
| **Node.js** | 22+ (LTS) | Для сборки frontend и инструментов разработки |
| **TypeScript** | 5+ | Строгий режим (`strict: true`) обязателен |
| **Vue.js** | 3.4+ | Только Composition API с `<script setup>` |
| **Redis** | 7+ | Кэш, сессии, очереди |

### Правила обновления

- При создании нового проекта — используй последнюю стабильную версию каждого компонента
- При обновлении существующего проекта — обновляй до максимально доступной версии, совместимой с текущим кодом
- Composer-пакеты должны быть совместимы с PHP 8.5+ и Laravel 12+
- npm-пакеты должны быть совместимы с Node.js 22+ и Vue 3
- При конфликте версий зависимостей — приоритет у базового стека (PHP, Laravel, Node.js)

## Внешние зависимости

### Общие правила

Добавление любой внешней библиотеки — это архитектурное решение. Каждая зависимость увеличивает поверхность атаки, усложняет обновление и создаёт риск при прекращении поддержки. Прежде чем добавлять пакет, убедись, что задача не решается средствами фреймворка или стандартной библиотеки.

### Критерии допуска

Пакет допустим к использованию, если выполняется **хотя бы одно** из условий:

1. **Доверенный вендор** — пакет принадлежит вендору из доверенного списка (см. ниже)
2. **Популярность + активность** — пакет соответствует **всем** критериям:
   - **≥ 400 000 скачиваний** (total installs на Packagist для PHP, weekly downloads на npmjs для JS)
   - **Активный жизненный цикл** — последний релиз не старше 12 месяцев
   - **Поддержка актуального стека** — совместим с PHP 8.5+ / Laravel 12+ (для PHP) или TypeScript 5+ / Vue 3 (для JS)
   - **Нет критических уязвимостей** — `composer audit` / `npm audit` не показывает unresolved high/critical

### Доверенные вендоры (Composer / PHP)

Пакеты от следующих вендоров допускаются без порога по скачиваниям, при условии активного жизненного цикла:

| Вендор | Namespace | Описание |
|--------|-----------|----------|
| **Spatie** | `spatie/*` | Экосистема Laravel-пакетов (laravel-data, laravel-permission, laravel-medialibrary, laravel-query-builder и др.) |
| **Symfony** | `symfony/*` | Компоненты фреймворка (console, http-foundation, mailer, validator и др.). Основа Laravel |
| **Orchid** | `orchid/*` | Платформа для административных панелей на Laravel |
| **ABSTechnology** | `abstechnology/*` | Корпоративные пакеты и интеграции |
| **Dskripchenko** | `dskripchenko/*` | Утилитарные пакеты и интеграции |
| **HFLabs** | `hflabs/*` | Качество данных, интеграция с DaData и сервисами обработки данных |
| **Opcodes** | `opcodesio/*` | Инструменты разработки для Laravel (log-viewer и др.) |

### Доверенные вендоры (npm / JS)

| Вендор | Scope | Описание |
|--------|-------|----------|
| **Vue.js** | `vue`, `@vue/*`, `@vitejs/*`, `pinia`, `vue-router` | Ядро frontend-стека |
| **Vite** | `vite`, `@vitejs/*` | Система сборки |
| **Tailwind** | `tailwindcss`, `@tailwindcss/*` | CSS-фреймворк (если используется в проекте) |
| **Vitest** | `vitest`, `@vitest/*` | Тестирование |
| **VueUse** | `@vueuse/*` | Коллекция composables для Vue |

### Запрещено

- Пакеты с 0 релизами (dev-only ветки без тегов)
- Пакеты, не обновлявшиеся более 24 месяцев (abandoned)
- Fork-и официальных пакетов без веских причин
- Пакеты, дублирующие функциональность фреймворка (Laravel / Vue / Node.js)
- Пакеты с неразрешёнными критическими уязвимостями

### Процедура добавления

1. Проверь, решается ли задача средствами фреймворка (Laravel helpers, Vue composables, Node.js std)
2. Проверь вендора — есть ли он в доверенном списке
3. Если вендор не доверенный — проверь количество скачиваний, дату последнего релиза, совместимость со стеком
4. Запусти `composer audit` / `npm audit` после установки
5. Зафиксируй lock-файл (`composer.lock` / `package-lock.json`) в git
