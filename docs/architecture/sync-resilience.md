## 1. Решение и границы

Предлагается следующий контракт:

1. Каждая локальная правка получает постоянный `mutation_id`, отдельный от UUID сущности.
   Сервер подтверждает конкретную правку; повтор запроса возвращает сохранённый результат.
2. Ошибки данных изолируются по мутациям. Некорректный draft сохраняется на устройстве,
   другие независимые изменения продолжают отправляться.
3. Pull сначала надёжно сохраняет входящие записи. При наличии локальной очереди или
   неразобранного draft серверная версия не замещает локальную.
4. Схема ответа и частичные коммиты вводятся в **`/api/v2/sync/*`**. Существующие v1
   клиенты и web сохраняют свои маршруты. Обе версии работают с теми же доменными данными.
5. До включения продолжения pull после сбоя push исправляются атомарность локальных
   записей, полнота сериализации и порядок публикации серверных ревизий.

Сохраняются local-first, серверное LWW по `updated_at`, UUID сущностей, tombstones,
снимки проигравших правок и лимит 500 изменений. CRDT, автоматического слияния полей,
изменения способа хранения web-токена и смены стека здесь нет.

**Почему v2:** обязательный ID операции, новый смысл подтверждения и частичные коммиты
меняют контракт. Простое добавление `rejected` в v1 не исправит старый клиент, который
удаляет строки по UUID сущности и может сразу выполнить незащищённый pull. Флаг в теле
v1-запроса также недостаточен: старый сервер проигнорирует его и выполнит запрос без
журнала подтверждений. Отдельный v2 URL на старом сервере вернёт 404 без записи данных.
Это соответствует [правилу версионирования](../07-api.md): v1 поддерживается минимум
три месяца после выхода клиента с v2, удаление v1 — отдельное решение.

Архитектурная альтернатива — расширение v1 по согласованному capability-протоколу —
потребовала бы отдельной защиты от смешанных версий серверов и всё равно не исправила
бы уже установленные клиенты. Для этого проекта рекомендуется отдельный v2 sync.

## 2. Инварианты

| Область | Обязательное свойство |
|---|---|
| Локальная правка | Доменная запись и outbox фиксируются одной SQLite-транзакцией |
| Подтверждение | Удаляется только строка с подтверждённым `mutation_id` из отправленного снимка |
| Повтор | Один ID с тем же содержимым не создаёт повторных эффектов/конфликтов/ревизий |
| Частичный ответ | У каждой входной мутации ровно один исход в `applied`, `conflicts` или `rejected` |
| Ошибка одной записи | Не откатывает уже подтверждённые независимые мутации |
| Локальный draft | Не стирается pull, в том числе при равном времени или серверном tombstone |
| Курсор pull | Продвигается только вместе с надёжно сохранённой входящей страницей |
| Серверный курсор | Не перескакивает через ещё не закоммиченную меньшую ревизию того же пользователя |
| Ошибка/карантин | Сохраняет исходный payload и причину; автоматического удаления нет |
| Аккаунт | Запоздалый ответ старой сессии не пишет данные/ack/курсор в новую сессию |

Признак успешной HTTP-доставки не означает, что все локальные изменения синхронизированы.
`push.cursor` из v1 нельзя присваивать `last_pulled_revision`: между push и предыдущим
pull могли появиться чужие изменения. Текущий mobile этого не делает — правило сохранить.

## 3. Контракт v2

### 3.1. Маршруты и включение

- `GET /api/v2/sync/capabilities`: `{ "data": { "protocol": "mutation-ack-v1", "max_changes": 500 } }`.
- `POST /api/v2/sync/push`: отправка и результаты по мутациям.
- `GET /api/v2/sync/changes?since=0&limit=200`: pull с ревизией каждой записи.
- Auth, настройки sync и общий формат ошибок наследуют v1; `user_id` берётся из токена.
  Версия v2 относится только к sync, остальные REST-маршруты остаются v1.

Клиент проверяет capabilities до первой отправки. 404/несовместимый protocol означает
«новая синхронизация недоступна»: очередь сохраняется, есть повтор проверки с backoff.
Для клиента, уже перешедшего на v2, автоматического downgrade на v1 нет. Старое приложение
продолжает v1; новое приложение сохраняет офлайн-работу при откате сервера без v2.
Capabilities и обе v2 операции включаются одним серверным feature flag только после
всех prerequisites. Каждый v2 ответ проверяется по protocol, HTTP 200 без него не ack.

### 3.2. Идентичность и запрос

Ключ операции — `(authenticated_user_id, device_uuid, mutation_id)`. UUID v4 мутации
создаётся один раз при локальной записи; SQLite `id` служит только для порядка очереди.
`entity_type + uuid` определяют сущность и не заменяют ID операции. Новый текст/операция/
updated_at означает **новый ID**, сетевой повтор использует прежний неизменный снимок.

```json
{
  "device_uuid": "11111111-1111-4111-8111-111111111111",
  "device_name": "Phone",
  "changes": [
    {
      "mutation_id": "22222222-2222-4222-8222-222222222222",
      "entity_type": "note",
      "uuid": "33333333-3333-4333-8333-333333333333",
      "operation": "update",
      "updated_at": "2026-09-30T10:00:00.000Z",
      "payload": {
        "title": "Покупки",
        "body": "Молоко",
        "color": "teal",
        "is_pinned": false,
        "is_archived": false
      }
    }
  ]
}
```

Payload v2 — снимок синхронизируемых доменных полей в snake_case, включая публичные
UUID родителей. Локальные `notification_id`, `calendar_event_id`, `user_id`, локальная
ревизия и внутренние ID в него не входят. Клиентский serializer явно преобразует
SQLite 0/1 в boolean; не отправляет сырую строку таблицы. Сервер сохраняет whitelist.
Правила типов, enum, nullable и длины выводятся из доменной схемы. Синхронизация старого
напоминания не должна отклоняться только потому, что его время уже прошло.

Envelope валидируется до любых записей: device UUID, массив до 500, объекты элементов,
уникальные корректные `mutation_id`. Нарушение → 422 всего запроса без эффектов.
Известный ID с ошибкой entity/operation/updated_at/payload получает per-change rejection;
валидация всех доменных полей через `changes.*` в глобальном FormRequest этому мешает.
Пустой batch допустим и возвращает три пустых массива.

### 3.3. Ответ и точное подтверждение

```json
{
  "data": {
    "protocol": "mutation-ack-v1",
    "applied": [
      {
        "mutation_id": "22222222-2222-4222-8222-222222222222",
        "entity_type": "note",
        "entity_uuid": "33333333-3333-4333-8333-333333333333",
        "server_revision": "145",
        "server_payload": {
          "uuid": "33333333-3333-4333-8333-333333333333",
          "title": "Покупки",
          "body": "Молоко",
          "color": "teal",
          "is_pinned": false,
          "is_archived": false,
          "created_at": "2026-09-30T09:00:00.000000Z",
          "updated_at": "2026-09-30T10:00:00.000000Z",
          "deleted_at": null
        }
      }
    ],
    "conflicts": [],
    "rejected": []
  }
}
```

| Массив | Поля элемента сверх `mutation_id` | Значение |
|---|---|---|
| `applied` | entity_type, entity_uuid, server_revision, server_payload | Доменная запись и receipt закоммичены |
| `conflicts` | Те же поля + conflict_uuid, client_payload | LWW проигран, клиентский снимок надёжно сохранён в sync_conflicts |
| `rejected` | code, retryable, entity_type/entity_uuid если валидны, errors? | Эта попытка не изменила доменные данные |

`errors` содержит публичные имена полей и стабильные коды, без SQL, стека, токенов или
содержимого чужих записей. Массивы — разбиение множества присланных ID: без пропусков,
дубликатов и посторонних ID. Клиент проверяет весь ответ **до** очистки очереди. Нарушение
→ protocol_error, ни одна строка этого batch не подтверждается; повтор безопасен по receipt.

V2 ревизии и курсор — неотрицательные десятичные **строки** (PostgreSQL bigint не должен
терять точность в JavaScript Number). Сравнение — по целому значению, не лексикографически
без учёта длины. Push не возвращает пригодного для продвижения pull-курсора.

Коды первой версии:

| code | retryable | Действие |
|---|---|---|
| invalid_payload / unsupported_entity / invalid_operation | false | Карантин снимка, исправление пользователем или обновлением клиента |
| mutation_id_reused | false | ID уже связан с другим содержимым; сохранить обе локальные версии, новый ID только для исправленной операции |
| parent_unavailable | true | Родитель пока не доступен; ждать его синхронизации, не сообщать, существует ли он у другого пользователя |
| predecessor_pending | true | Предыдущее изменение этой сущности не обработано; сохранить порядок |
| retry_later | true | Только известная временная ошибка после полного rollback операции |

Сетевая ошибка, HTTP 5xx, отсутствие/повреждение ответа означают **неизвестный результат**:
ничего не удалять и повторять прежние ID. При 401/403 прекращаются запросы до восстановления
доступа/разрешения sync. 429 учитывает Retry-After и не переводит данные в терминальный
карантин. Неожиданный Throwable не маскируется как «плохая запись».

### 3.4. Серверная транзакция, replay и зависимости

Таблица `sync_mutation_receipts`: user_id, device_uuid, mutation_id, request_hash,
state (`waiting`/`terminal`), terminal_result JSON nullable, created_at, updated_at;
unique(user_id, device_uuid, mutation_id), FK user с удалением при удалении аккаунта.
Hash вычисляет сервер по каноническим entity/uuid/operation/UTC updated_at/payload:
рекурсивная сортировка ключей объектов, сохранение порядка массивов и типов/null.
Сеть/имя устройства в hash не входят. Клиент не меняет payload старого ID.

Каждое изменение обрабатывается **своей** DB::transaction без внешней транзакции batch:

1. Взять общую блокировку записи пользователя (§ 5.2), затем прочитать receipt.
2. Другой hash → mutation_id_reused; исходный receipt остаётся неизменным.
3. Terminal receipt → вернуть сохранённый результат без повторного save/backup/revision.
4. Проверить вход, владельца, родителя и LWW; выполнить изменение или сохранить конфликт.
5. Записать terminal receipt в той же транзакции, что данные/конфликт; commit до ответа.

При parent_unavailable сохраняется hash/state=waiting, без терминального результата.
Тот же ID с тем же снимком позднее переоценивается: родитель мог уже появиться.
Иначе «повтор отклонения навсегда» сделал бы зависимую запись невосстановимой.
Известные ошибки constraints откатываются до формирования rejection; неизвестные ошибки
прерывают запрос с 5xx. Уже закоммиченные предыдущие мутации восстанавливаются по receipts
при повторе всего batch. В памяти после rollback нельзя повторно использовать изменённую
Eloquent-модель. Вложенные savepoints не заменяют независимый commit каждой операции.
Это уточнение исходного предложения DEV-24 о savepoint на изменение: короткая отдельная
транзакция сокращает время удержания user lock и делает receipt завершённым сразу.
Цена — до 500 commit на запрос; перед выпуском измерить задержку/нагрузку полного batch
на staging. При смене стратегии транзакций сохранить тот же внешний контракт и тесты.

Сервер сохраняет входной порядок. Неуспех блокирует последующие изменения **той же
сущности** в этом batch; независимые ключи продолжаются. Если parent создаётся позже
child, child получает parent_unavailable, parent может примениться, child повторяется
в следующем цикле. Неизвестный и чужой parent имеют одинаковый ответ.
Существующий parent с tombstone допускается как в текущем LWW; не реанимируется неявно.
Явная неверная ссылка при update отклоняет операцию, а не молча оставляет прежний FK.

Delete существующей строки создаёт обычный tombstone. Delete неизвестного UUID требует
валидного снимка для создания tombstone; пустой/неполный снимок → invalid_payload,
не «applied без записи». Orphan delete → parent_unavailable. Так поздний более старый
create сравнивается с сохранённым tombstone. Новые записи не создаются с выдуманными
родителями или заполнителями обязательных доменных полей.

`RegisterDeviceAction` и last_synced_at — метаданные доставки, не доказательство полного
pull. В v2 их ошибка после commit не отменяет receipt. Журнал не очищается по TTL: клиент
может вернуться после долгого офлайна. Первую версию выпускать с мониторингом роста;
политика compaction/retention требует отдельного handshake и не входит в DEV-24.

## 4. Локальное хранение и pull

### 4.1. SQLite и исходящая очередь

Расширить `sync_outbox`: mutation_id UNIQUE, owner_uuid (nullable только для гостя),
state (`pending`, `waiting`, `quarantined`), next_attempt_at, last_error_code.
Существующие id/payload/updated_at/attempts сохраняются. Миграция присваивает ID старым
строкам ровно один раз и не очищает очередь. Отправленные снимки неизменяемы.

Новая таблица `sync_drafts` хранит исходную мутацию, причину, серверный снимок при наличии
и решение пользователя. Это долговечная история исправленных/отклонённых/конфликтных
версий. Нет автоматического TTL. Quarantined outbox остаётся защитой текущего draft;
архив уже разрешённого конфликта сам по себе не блокирует будущий pull.

Доменное изменение + outbox выполняются одним **синхронным** Drizzle transaction callback:
`.run()/.get()/.all()`, без await и сетевых/notification вызовов внутри. Установленный
Expo-драйвер Drizzle 0.38.4 коммитит сразу после возврата callback, не ожидая Promise.
Уведомления обновляются после commit, с повторной сверкой после запуска приложения.
Для одной сущности новый local updated_at = max(текущее время, предыдущая локальная
метка + 1 ms), чтобы две быстрые правки не имели одинакового LWW-времени.
Между устройствами сохраняется прежний LWW и его ограничения при неверных часах.

Обработка ack одной SQLite-транзакцией: сохранить canonical server payload/ревизию в
приёмном журнале, сохранить локальный снимок конфликта при необходимости, удалить только
точные подтверждённые mutation_id, затем попытаться применить доступную серверную версию.
Новая правка той же сущности, появившаяся за время HTTP-запроса, остаётся в outbox и UI.
Если локальный commit ack не состоялся, повтор отправки получает тот же server receipt.

Снимок прохода ограничен верхним id; новые записи идут в следующий проход. Не больше
500 на запрос. Следующие batch строятся с учётом результатов предыдущего: ожидание или
карантин старой правки не позволяет отправить последующие правки того же ключа вне
порядка. Независимые сущности и pull продолжаются. Parent-dependent retry возобновляется
после изменения зависимости; сетевые retries ограничены, с backoff/jitter, без busy loop.
Повреждённый JSON одной outbox-строки сохраняется в карантин до сериализации batch.

### 4.2. Входящий журнал и курсор

Новая таблица `sync_inbox` хранит owner_uuid, entity_type, entity_uuid, server_revision
(TEXT), server_payload, state (`ready`, `deferred`, `apply_error`) и last_error_code.
Ключ версии: owner + type + UUID + revision. Хранятся необработанные версии; после
успешного применения можно удалять более старые версии того же ключа. Одна только
новая ревизия не повод удалить старый снимок, пока новый ещё не удалось применить.
Отдельный `sync_entity_versions` хранит максимальную применённую серверную ревизию.

Pull v2 сохраняет группировку v1 по пяти сущностям, но каждая запись содержит
`server_revision`; meta содержит protocol, cursor и has_more. `since` и cursor — строки.
При первом переходе на v2 отдельный ключ `last_pulled_v2_revision` начинается с "0". Старые локальные
draft/outbox не удаляются; full pull использует ту же защиту pending данных.

Обработка страницы:

1. Проверить protocol, структуру, типы, revision и непротиворечивость cursor/has_more.
   cursor ≥ since; каждая revision > since и ≤ cursor; при has_more=true cursor
   должен строго расти. Неизвестный/неразбираемый envelope → курсор не меняется.
2. Одной короткой SQLite-транзакцией записать **все** входящие snapshots в inbox и
   новый v2 cursor. Если запись/диск/commit не удались — rollback страницы и курсора.
3. Вне сети применить inbox, в порядке parent → item → comment. Каждый upsert и отметка
   его server_revision атомарны. Ошибка остаётся в inbox, без «console.warn и забыть».
4. При pending/waiting/quarantined локальной мутации того же ключа оставить server
   snapshot как deferred. Метки времени не отменяют эту защиту, tombstone тоже.
5. После ack/исправления/решения пользователя снова обработать deferred. Если чистая
   запись имеет уже принятую большую/равную revision, старый replay не замещает её.
   Для чистой записи canonical server state принимается по revision; старое локальное
   LWW-время не должно бесконечно удерживать проигравший серверу draft.

Защита распространяется на зависимости: pending child/comment удерживает разрушительное
применение tombstone его parent и всей цепочки предков. Tombstone parent без локальных
изменений может скрыть дерево в UI, но не должен физически каскадно удалить draft/inbox.
Если parent ещё не пришёл из другой страницы, child сохраняется в inbox до parent.
Сбой одной записи не блокирует получение независимых данных, поскольку исходный snapshot
уже сохранён. Рост inbox ограничивается ресурсами устройства: при нехватке места получение
новых страниц приостанавливается с видимым сообщением, курсор не продвигается без записи.

```mermaid
sequenceDiagram
  participant UI as Локальное редактирование
  participant DB as SQLite
  participant API as Sync API v2
  UI->>DB: Доменная запись + mutation_id (одна транзакция)
  DB->>API: Неизменный снимок M1
  UI->>DB: Новая правка M2 того же объекта
  API-->>DB: Ack только M1 + серверная версия
  DB->>DB: Сохранить версию, удалить M1, оставить M2
  DB->>API: Pull от последнего принятого cursor
  API-->>DB: Страница изменений
  DB->>DB: Inbox + cursor атомарно; M2 защищает локальный draft
```

### 4.3. Частичный успех, аккаунты и интерфейс

SyncResult различает `complete`, `partial`, `failed`; содержит applied/conflict/rejected/
waiting/deferred counts, ошибки push/pull отдельно. last_pulled_at отмечает доставку,
last_synced_at — только завершённый цикл без неразобранных исходящих правок и apply_error.
Конфликты с надёжным backup показываются отдельно, не требуют вечного повторного push.

После ошибки push можно вызвать pull **только после внедрения inbox/защиты draft** и
проверки, что аккаунт/токен/поколение локальной БД не изменились. 401/403, отключение sync
или смена аккаунта прекращают текущий цикл. token/account/database_epoch фиксируются
при старте, перепроверяются перед каждым запросом и SQLite-транзакцией. Database epoch
— новый случайный UUID после reset, а не счётчик, снова начинающийся с нуля. Старый ответ
не очищает новую очередь; новый аккаунт не получает снимок старого outbox.

В настройках синхронизации показать число несохранённых в облаке правок и понятные действия:
исправить данные, повторить после восстановления связи/родителя, сохранить отдельную копию,
явно отказаться от локальной версии. Отказ сначала архивирует payload; автоматического
удаления после N попыток нет. Исправление создаёт новый mutation_id, заменённые версии
остаются в sync_drafts; старые quarantined строки снимают блокировку только атомарно
с сохранением нового pending snapshot или явным выбором серверной версии.

Logout проверяет **фактические** pending/waiting/quarantined и незавершённые входящие
ошибки, а не отсутствие исключения от push. Существующее подтверждение удаления локальных
данных распространяется на новые таблицы. resetLocalData должен включать comments,
inbox/drafts/versions и выполняться правильной синхронной транзакцией. Отзыв токена из-за
401 сам по себе не удаляет локальные draft. Гостевые данные получают owner при первом
входе по существующей политике; данные прежнего аккаунта гостевыми не считаются.

## 5. Предварительные исправления и порядок DEV-24

### 5.1. Полнота данных

До принятия canonical snapshots покрыть round-trip всех полей `SyncEntities::FIELDS` и
ссылок родителей. Сейчас serializer теряет `note.color` и `shopping_list_item.quantity`,
`deadline`, `reminder_at`, `link`, `comment`, `tags`; mobile подставляет null/1.
Это блокер принятия canonical state. Добавление отсутствующих полей в v1 ответ обратно
совместимо; исправление рендеринга всех цветов остаётся отдельной MOB-66.
Нормализация status/is_checked и derived parent status должна оставаться симметричной;
server-derived parent update имеет собственную revision и приходит через обычный pull.

### 5.2. Порядок серверных ревизий

Одной PostgreSQL sequence недостаточно: A получает revision 10 и ещё не commit,
B получает 11 и commit, pull продвигается до 11, после commit A запись 10 пропущена.
Сценарий воспроизведён на существующем SyncPullService (§ findings).

Для текущего масштаба проекта предлагается общий `SyncWriteGuard`:

- Любая транзакция изменения sync-данных сначала блокирует строку своего user
  через SELECT FOR UPDATE и лишь затем читает/меняет доменные строки и берёт nextval.
- Guard обязателен для REST v1, push v1/v2, observer/derived status, soft delete,
  hourly purge, административных и импортирующих команд. Вложенные actions используют
  тот же connection/transaction; один порядок блокировок: user → domain.
- V2 pull в короткой READ COMMITTED транзакции сначала берёт FOR SHARE на того же user,
  затем собирает и сериализует все пять типов. Все SELECT выполняются после lock.
  До завершения страницы sync-writers этого пользователя не меняют её данные.
- Sequence и текущие server_revision сохраняются, в том числе пропуски номеров после
  rollback. Между разными пользователями транзакции остаются параллельными.
- Deadlock/lock timeout → rollback всей операции, ограниченный retry, без частичного ack.
  Внутри lock нет внешнего HTTP/уведомлений. Hard delete аккаунта и cascade подчиняются
  тому же порядку. Прямые SQL/import-операции — только через guard либо при выключенном
  sync в maintenance, не конкурентно с работающими клиентами.

Это прикладной протокол блокировок, а не автоматическое свойство PostgreSQL. До его
активации обязателен inventory всех writer paths и конкурентный тест REST/push/purge/pull.
Пропущенный writer нарушает гарантию; v2 flag не включается до покрытия этих путей.
Один лишь REPEATABLE READ у pull или глобальный max(sequence) проблему не исправляют.
Глобальная блокировка всех пользователей и новый CDC/change-log для этого этапа не нужны.

### 5.3. Этапы с отдельными проверками

| Этап | Изменения | Условие перехода |
|---|---|---|
| DEV-24/A | Round-trip serializer; атомарные local CRUD/outbox/reset; синхронные транзакции | Сбой enqueue не оставляет доменную запись без outbox; полный payload сохраняется |
| DEV-24/B | Inventory writers + SyncWriteGuard; безопасное чтение ревизий | Две конкурентные транзакции не теряют запись; REST и purge соблюдают guard |
| DEV-24/C | Additive receipts, v2 validation/push/pull/capabilities; feature flag off | Пооперационная изоляция, replay, LWW/parent/tombstone и v1 regression tests |
| DEV-24/D | SQLite upgrade, typed ack, inbox, quarantine, account/logout и состояние UI | Crash/restart, pending-edit/pull, переход аккаунтов, upgrade populated DB |
| DEV-24/E | Staging matrix old/new; ограниченный выпуск backend → mobile | Все приёмочные сценарии, CI, ревью и наблюдение метрик; затем включение v2 |

Backend-only выпуск v2 до нового mobile сохраняет v1. Legacy guard для orphan в v1
не объявляется надёжным подтверждением; его исправление по принципу «не сообщать applied
без записи» требует отдельного regression сценария для старого клиента. Безопасный вариант:
422 и rollback всего v1 batch, сохранение outbox; не вводить частичный успех для v1 молча.
Такой safety fix включить в план выпуска с явным сообщением о возможном ожидании обновления
у старого клиента с повреждённой очередью. Возможности частичного восстановления — у v2.

Rollback после additive миграций не удаляет receipts/inbox/drafts. После включения v2
не возвращать сервер к версии, которая пишет без SyncWriteGuard: при аварии сначала
приостановить v2 через flag, сохранить очереди; откатывать к совместимому baseline этапа C.
Мобильный binary downgrade после появления v2-очереди не поддерживается до отдельной
проверки совместимости: старый клиент может игнорировать state/ID и повторно отправить draft.
Перед production миграциями — отдельный проверенный backup/rollout, как в OPS-14.

Метрики без содержимого заметок: applied/conflict/rejected по code, replay count,
oldest pending age, waiting parent, inbox apply_error, protocol mismatch, lock wait,
размер receipts/inbox. HTTP 200 с неразобранными правками не рисуется как «всё сохранено».

## 6. Приёмочные сценарии

| № | Сценарий | Ожидаемый результат |
|---|---|---|
| 1 | Две правки одного UUID в batch, одна отклонена | Удаляется только подтверждённый mutation_id |
| 2 | Одинаковый UUID у note/reminder | Подтверждения не пересекаются между типами |
| 3 | M2 создана во время запроса M1 | M2 и текущий текст сохранены после ack и pull |

| 22 | Constraint при применении сохранённого snapshot | apply_error в inbox; snapshot доступен для повторной обработки |
| 23 | Ack принят, crash до локального commit | Outbox остаётся; replay и атомарная локальная обработка завершаются |
| 24 | Старый ack snapshot после более нового pull | Применённая server_revision не регрессирует |
| 25 | A взяла меньшую revision, B пытается commit раньше | Для одного user guard не допускает пропуска A; другие users независимы |
| 26 | Конкурентные REST, v1/v2 push, soft delete и purge | Общий guard, корректные tombstones и derived parent revisions |
| 27 | Приняты все поля заметки/пункта → pull → mapper | Цвет, количество, даты, ссылки, теги и комментарий не теряются |
| 28 | Logout с rejected/waiting при HTTP 200 | Guard предупреждает о фактически неотправленных данных |

| 30 | Миграция populated DB с guest/outbox/tombstones | ID устойчивы, drafts сохранены, v2 pull начинается с 0 |

Граница доказательств: текущие дефекты воспроизведены отдельно; этот документ не является

моки Jest не доказывают атомарность Expo driver. Независимое ревью ещё не выполнено.
