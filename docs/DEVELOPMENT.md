## Цель продукта и ближайшего цикла

Приложение помогает записывать заметки, вести задачи и покупки, получать напоминания
и видеть календарь. Mobile работает локально без аккаунта и сети; облако обеспечивает
синхронизацию и восстановление. Web — клиент серверного API, а не офлайн-копия mobile.

Ближайшая цель: надёжная синхронизация без потери локальных правок и воспроизводимые
проверки перед выпуском. Новые функции уступают восстановлению этих гарантий.
Критерии: большая очередь выгружается, новые правки сохраняются во время запроса,
ошибки отдельной записи диагностируются, проверки относятся к выпускаемому коммиту.

## Порядок работы

1. Прочитать текущую задачу и проверить состояние Git; выбрать один законченный результат.
2. Зафиксировать ID, область, критерии приёмки и зависимости в TASKS.md.
3. Работать в отдельном worktree, соблюдать стандарты затронутого слоя.
4. Для бага воспроизвести сценарий, реализовать исправление и проверить регрессию.
5. Проверить diff, типы и тесты. Изменения sync дополнительно проверять на сохранность данных.
6. Записать результат, команды, ограничения и следующий шаг; подготовить коммит.
7. Выпуск учитывать отдельно: локально проверенная ветка ещё не означает выкладку.

Роли DEV/MBE/MOB/WEB/OPS сохраняют предметные обязанности. В одной сессии координатор
может выполнять несколько ролей последовательно. ARCH требуется для нового контракта,
схемы или существенного решения; небольшой багфикс не проходит все 12 ролей.
REVIEW/SEC — отдельная проверка по риску; если её выполняет автор, это самопроверка.
UI-проверка нужна при изменении интерфейса. Независимое ревью остаётся желательным
условием выпуска изменения синхронизации, но в этом цикле оно не выполнялось.

TASKS.md обновляет один координатор. ID резервируется при создании задачи; Completed
считается по записям с `Статус: completed`, совместная запись нескольких ID считается
одной записью. Рекомендации и незавершённый релиз не записываются как выполненные.

## Проверки

По указанию пользователя изменения sync проверяются также со стороны mobile.
Для затронутого сценария нужны вызовы реальных сервисов/хуков и проверка SQLite/outbox,
полей, читаемых экранами, повторов/офлайн и выхода/смены аккаунта. Копия алгоритма в
тесте не считается проверкой приложения. Условия успешной проверки и известные пробелы
записываются в отчёте; HTTP/native mocks и Node SQLite не объявляются тестом на устройстве.

Из своего worktree:

```bash
npm run typecheck --prefix mobile
npm test --prefix mobile -- --runInBand
npm run typecheck --prefix web
npm test --prefix web -- --maxWorkers=2
VITE_API_URL=/napominalki npm run build --prefix web -- --base=/napominalki/
git diff --check
```

Backend: PHP 8.5, PostgreSQL 17, отдельная БД `reminders_test`, валидный тестовый APP_KEY,
`php artisan test --compact`. Конфигурация нового CI находится в `/.github/workflows/ci.yml`.
Она создаёт `.env.testing` из `.env.example`, генерирует тестовый ключ и использует
PostgreSQL service. Старый `.env.testing` на сервере не является переносимым окружением.

В текущем цикле базовый backend проверялся в `reminders_app` на исходном коммите:

```bash
docker exec -e APP_ENV=testing -e DB_DATABASE=reminders_test -e DB_URL= \
  -e APP_KEY=base64:AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA= \
  reminders_app php artisan test --compact
```

Указанный ключ — только тестовая фикстура. Не менять APP_KEY рабочего сервиса ради тестов.
Перед такой командой проверить отсутствие `bootstrap/cache/config.php`, иначе Laravel
может использовать закешированное подключение вместо тестового. Для backend-изменений
в worktree нужен отдельный контейнер с кодом именно этой ветки и отдельной тестовой БД.

При подготовке этой копии mobile/web node_modules подключены симлинками к исходной
копии. Проверки используют установленные зависимости; чистую установку проверять через
`npm ci` в новом окружении. Не запускать установку пакетов через общий симлинк.
